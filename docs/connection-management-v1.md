# Local connection management V1

The Integrations page is a trusted local operator tool, not production tenant authorization. The API binds to loopback and uses the existing operator session, Host/peer checks, HttpOnly cookie and Origin checks. There is no browser credential entry, account deletion or transfer.

Configure the API process with `MOYSKLAD_TOKEN` and `MOYSKLAD_ACCOUNT_ID`, or `OZON_CLIENT_ID` and `OZON_API_KEY`. Restart the API after changes. Do not commit tokens or API keys or put them in URLs. Each card reports configuration availability without returning secrets. Existing tenant registrations remain visible through the existing scoped registrations API.

For local development, start PostgreSQL and apply migrations as described in the README. Export the provider settings and `STYK_OPERATOR_SECRET` in the API process's environment, run `go run ./cmd/api`, and run `npm ci` and `npm run dev` in `web`. Open the loopback address printed by Vite. No marketplace settings are needed to view unconfigured cards or run automated tests.

Choose a tenant and explicitly press Test connection. MoySklad uses one GET of `/entity/product` with limit 1; Ozon uses the read-only POST `/v3/product/list` with limit 1. The shared provider clients enforce rate limiting, reject redirects and make at most one attempt with a five-second request timeout and six-second overall deadline. No automatic probes or imports are performed. Verification status is held only in the current local session and describes the bounded API read, not account ownership, complete permissions, or synchronization readiness. A MoySklad returned product can corroborate the configured account ID; an empty collection cannot. Ozon's probe does not independently establish ownership. Failed or mismatched responses are sanitized.

`NOT_CONFIGURED` means the required local settings are absent or invalid; `CONFIGURED_NOT_VERIFIED` means no probe has run in this session. `VERIFIED` means the bounded read succeeded, while `VERIFICATION_FAILED` includes a sanitized reason. The registration status is separate: `REGISTERED`, `NOT_REGISTERED`, `OWNERSHIP_CONFLICT`, or `NOT_CHECKED`. A completed import does not imply current connectivity or an authoritative stock snapshot. Status is not shared with other sessions and disappears on process restart.

Within five minutes of a successful check, explicitly acknowledge that the configured account belongs to the selected tenant and press Register account. The server resolves the account exclusively from its startup configuration, checks existing ownership and atomically calls the existing registration service with `LOCAL_OPERATOR_SESSION` provenance. No historical imports are implicitly included. A source account is unique across tenants and cannot be transferred here. The shared session audit identifier is not an individual human identity. A successful probe is not registration consent.

After a lost or uncertain response, use Check registration outcome. The server reads the exact configured registration before another write, including on retries. If the database cannot be queried, the outcome remains unknown. For an existing registration, the scoped view displays eligible persisted import counts and age. Successful traversal is not an atomic snapshot, live connectivity or exhaustive visibility; missing stock rows are unknown. Links open the existing product, warehouse and diagnostics views.

`GET /api/integrations?tenant=...` returns local provider status, configured account identifiers and scoped registration/import summaries. Authenticated `POST /api/integrations/{provider}/probe` and `POST /api/integrations/{provider}/register` require the local Origin and JSON; the latter accepts only `tenant` and `acknowledge`. `GET /api/registrations` returns account IDs registered to the selected tenant. The local console may display these external identifiers, including the Ozon client ID, to an authenticated local operator. An account identifier is not an API key and does not authorize access; the server checks registration and account scope for business-data queries. The local operator secret grants access to the trusted local workspace, not individual tenant authorization.

Marketplace API keys and bearer tokens remain server-side; the endpoints do not return them or raw provider payloads. Future production work needs individual authentication, tenant authorization, credential management and a separately designed opaque connection-identifier boundary. None is supplied here.

The connection browser test uses synthetic in-process provider servers and a disposable local PostgreSQL database named `styk_connection_v1_test`. After applying migrations and installing the frontend dependencies and Playwright browser, run `STYK_BROWSER_E2E=1 go test -tags=integration -run TestConnectionBrowser ./internal/console` with `TEST_DATABASE_URL` pointing to that database. It starts a temporary loopback Vite server and performs no live marketplace requests.
