# MoySklad customer-order reservation evidence

This milestone reads customer orders; it does not create documents, modify reservations, publish inventory, or establish that an order reserve is included in a particular stock-report baseline. No live MoySklad request was made during development.

## Verified API contract

The official [customer-order specification](https://raw.githubusercontent.com/moysklad/api-remap-1.2-doc/master/md/documents/_customerOrder.md) describes these read methods:

* `GET /entity/customerorder`: a collection with `meta.size`, `limit`, `offset` and `rows`; `updated` supports comparison filters.
* `GET /entity/customerorder/{id}`: one customer order, with a document UUID and account UUID. `syncId` is an optional synchronization UUID; `externalCode` is an external code, with no documented Ozon identity semantics. `created`, `updated`, `deleted`, document `moment`, `applicable`, `state` and `store` are separate fields. `applicable` is the document-posting flag, not a cancellation status; a deletion timestamp is not inferred from absence.
* `GET /entity/customerorder/{id}/positions`: a paginated position collection. Each position has its own ID and account, an assortment reference, `quantity`, `reserve`, and reported `shipped`; the latter is described as delivered in the specification. `pack` can contain a pack ID, unit reference and quantity. Product, variant, service, batch and bundle identities are distinct. A reserve field describes that position; it does not specify the set of reservations in a stock report.

The official [general API documentation](https://dev.moysklad.ru/doc/api/remap/1.2/) says creation/update date-time fields use Moscow time and describes filtering and access restrictions. The CLI accepts an explicit RFC3339 interval of at most 31 days, aligned to milliseconds, and sends `updated >= from; updated < to` in Moscow time. Source date strings are retained separately from local response-receipt timestamps. Their timezone/precision semantics do not establish the order of individual position changes. Visibility depends on the account's permissions; empty results do not verify account ownership or exhaustive visibility. Deleted documents may be omitted or inaccessible; this importer does not claim deletion coverage.

The existing HTTP client enforces a GET-only path allowlist, timeouts, cancellation, rate limiting, bounded retries and documented MoySklad retry headers. Both order and position pages must have consistent metadata and no duplicate IDs; a changed list/detail `updated`, interrupted page, wrong account, invalid identity or unsupported assortment type fails the whole import. Completed traversal is not an atomic snapshot, and updates can occur after the detail read or between pages. Whether every position or reserve change advances the parent `updated` field needs further contract verification; the window cannot prove complete change coverage. A missing position or order is not zero or deletion. Each successful import appends a batch, even if content is unchanged; source observations are not deduplicated by content or reordered by local insertion time. Large imports are held in memory and committed under the configured database timeout.

## Data and privacy

Migration 15 records tenant/account-scoped import batches, customer-order identities, immutable order observations and position observations. Observation and position inserts must occur in the batch's transaction, so a committed observation cannot silently acquire later positions. It preserves original IDs, optional synchronization UUID, document warehouse and state IDs, source dates, posting flag, local order/position observation times, assortment kind/ID, nullable quantity/reserve/shipped, and nullable pack information. Missing reserve is NULL; an explicit `0` remains `0`. Product and variant IDs never collapse. Numeric values retain PostgreSQL decimal precision. No customer name, address, phone, email, comment, order name, raw response, or untrusted `externalCode` is stored. Identifiers themselves are business data and require appropriate access control.

Both accounts must be explicitly registered to the same tenant before correlation; the importer checks MoySklad ownership before any HTTP request and the transaction enforces it again. Registrations and the CLI are a trusted local administrator boundary, not end-user authentication or row-level security. A database owner can bypass application checks and alter schema. The same exact external account ID cannot be assigned to two tenants by the registry, but aliases are not independently resolved. No historical import is silently assigned to a tenant.

## Correlation and uncertainty

The read-only evaluator selects an explicit Ozon posting observation and completed customer-order batch. It requires current confirmed product and warehouse mappings for the correct tenant/account pair, checks the Ozon SKU against the authorized latest catalog, and preserves mapping IDs and versions with matched position IDs. A same-item, same-warehouse order is only `CANDIDATE_ONLY`; two or more are `AMBIGUOUS`. Missing mappings or a matching position with no document warehouse give `INSUFFICIENT_EVIDENCE`. A SKU/mapping conflict or incompatible/newer source observation gives `CONFLICT`. `NOT_FOUND` means only that no candidate was found in the selected bounded traversal, not that no customer order exists.

No official source examined here establishes a direct Ozon-posting-to-MoySklad-order identity. Order name, `externalCode`, `syncId`, quantity, amount and timestamp coincidences are never used to confirm identity. The `CONFIRMED_BY_EXPLICIT_IDENTITY` outcome is reserved for a future independently verifiable source; no current production connector or CLI can assert it. A sealed synthetic verifier exercises that branch in tests and cannot be supplied through the administrative CLI. Even an eventual confirmed identity would establish only posting-to-order identity, not source reserve or stock-baseline inclusion.

Candidate evidence can show a source position and a nullable reported reserve; it does not prove the position matches a particular posting line, that a reservation belongs to Ozon, that a warehouse was assigned for every reserve, or that the reserve was reflected in a given baseline. Another sales channel can create an indistinguishable reservation. Two orders can have the same products, warehouse, quantity or date. Split postings, partial shipment, cancellation, missing rows, delayed updates and out-of-order observations require independent evidence. Identical repeated observations remain separate. The evaluator reports newer source revisions and different content at an equal or unknown source timestamp as conflicts; it never treats import ID as source-event order.

Stock decisions inspect at most ten relevant postings from the selected latest Ozon batch and at most 100 candidate orders / 1,000 matched position-mapping entries per correlation. Truncation is reported as insufficient evidence. The latest customer-order batch is a bounded update window, not an exhaustive active-order set. Decisions retain its scoped batch reference and frozen correlation summary. A reported reserve may improve the explanation, but `CUSTOMER_ORDER_BASELINE_INCLUSION_UNKNOWN`, `RESERVATION_ATTRIBUTION_UNKNOWN`, and unassigned/competing coverage remain unresolved; production `READY_CONDITIONAL` remains prohibited by the existing database constraint.

Before reservation overlap can be solved, STYK needs an authenticated source of posting-to-order identity, a line-level crosswalk to source reservation/movement records, a proven compatible stock baseline and source ordering, and coverage of unassigned and unrelated reservations. No manual assertion in this milestone creates these proofs.
