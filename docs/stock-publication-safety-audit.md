# STYK stock publication safety audit

## Controlled test-account exception (2026-10-29)

The findings below remain the production safety assessment. An explicitly enabled, owner-authorized test policy permits the normal worker to address only the fixed `cross-e2e` account pair and mappings explicitly enrolled in the current, expiring operator-audited policy, with an integer quantity from 0 through 10 and each target's configured maximum. The exact account pair is compiled into `internal/testpublication/policy.go`; a deployment switch cannot authorize another real account. The legacy manual exception retains its original fixed target and seven-unit limit. Scheduled test synchronization does not release the general production hold.

Each publication is recorded with a one-attempt PostgreSQL outbox task before dispatch. An automatic cycle completes one pair of durable imports, applies the existing calculator independently for each target and creates a fresh decision only when a supported target differs from the observed marketplace quantity. Its publication associations are durable and immutable; one uncertain target is fenced without preventing other eligible targets from progressing. Standing assumptions are explicitly `OPERATOR_ATTESTED`, retain their original acceptance time and expire within 24 hours; they are not new provider observations. A claimed task and the exact one-shot adapter intent are checked for scoped lease, mapping, current policy, quantity and evidence immediately before the HTTP attempt. Lease expiry or an ambiguous provider response is fenced as UNKNOWN and never automatically retried. A positive per-target acknowledgment is recorded separately from a matching provider readback; a mismatch or unavailable readback stays fenced for investigation. A matching readback describes the returned state, not causality. The database lease cannot prevent an already dispatched request from arriving later, nor can local data guarantee an atomic provider snapshot, buyer isolation, complete orders, or absence of external writers. The owner accepted possible buyer exposure. The resulting exception is not approval for unrestricted customers or production rollout.

Manual and automatic controlled writes both require a single-use intent. After the client waits for its rate limit, it rechecks the outbox claim and evidence. That check acquires the scope, credential, import and mapping locks before taking its database snapshot, and releases them before the HTTP request. It requires a PostgreSQL connection that remains attached to the same backend session for the entire check; transaction-pooling proxies must not be used for this path. A state change after the last check can still race with the external request.

For the original manual target or a target enrolled in an audited automatic test policy, an authenticated operator may explicitly accept an unresolved outcome and authorize a new review. The original UNKNOWN operation and failed task remain unchanged; a separate immutable recovery audit records the latest bounded readback, session, reason and accepted uncertainty, and a separate immutable link records the first new publication. Active target dispatches and recent test-worker heartbeats block this action. The operator also asserts that the previous worker is stopped. A heartbeat cannot establish that a paused worker or a request already at Ozon has terminated, and this recovery provides no provider-side ordering guarantee. A fresh operator attestation or reauthorized test policy and both provider traversals after the recovery event are required before a new publication decision.

Date: 2026-10-29. Audited baseline: `1d3d8ee656d6346e32347fc0cafc7023318acff1` plus the corrections in this commit. Recommendation: **NOT READY** for real Ozon publication. Synthetic tests are not evidence of production safety.

## Scope and immediate containment

The formerly running local API and worker from the previous preview session were stopped before the audit so the old, ungated worker could not initiate stock writes. Tests use synthetic credentials, local PostgreSQL test databases and loopback HTTP servers. No real marketplace write was attempted. Production data and credentials were not modified by these tests.

At the audited baseline there was a **hard safety hold on real stock writes**, not merely a flag default. The controlled exception above is the sole later change to that baseline. The worker still defaults to a no-op for publication, and `STYK_STOCK_PUBLICATION_ENABLED=true` alone cannot enable real writes. Only the combination of this flag and `STYK_STOCK_PUBLICATION_TEST_ENDPOINT` specifying an explicit literal loopback HTTP address and port enables simulator operation. The simulated worker uses fixed synthetic credentials, not stored or environment marketplace keys. Even in simulator mode, the API reports `publication_available:false` for real-marketplace UI. The browser treats an absent availability field as unavailable.

The hold is required because a database check and an external HTTP write are not atomic, and because the precise current provider contract, delayed application and freshness guarantees could not be established. Existing database policies are not deleted or silently changed; with the gate off they cannot be claimed or dispatched. The disabled runner does not automatically age DISPATCHING jobs into UNKNOWN; an operator can invoke the existing explicit read-only reconciliation for a timed-out dispatch. Deployment must stop **all old worker binaries**, not just restart the API; an old already-dispatched request cannot be physically cancelled by these changes.

## Architecture and actual triggers

At the baseline, `StockSyncControls` allowed an operator to preview, explicitly acknowledge and enable a frozen scoped review. The same-origin, JSON and authenticated local-operator checks in `auth.authorized`/`connectionMutation` preceded `stockSyncAPI.preview`/`mutate`. A preview derived bounded targets from confirmed mappings, current imported evidence and explicit attestations; `MutateStockSync` locked the scope, checked its idempotency ledger and the review/evidence snapshot, then atomically saved enabled intent and `QUEUED` publication targets.

`application.Worker.Run` called `stocksync.Runner.RunNext`. `RefreshStockSync` reevaluated up to five enabled scopes, potentially enqueueing a changed quantity after a newly completed eligible import; an existing enabled policy could therefore cause an external request without a new click. `NextStockPublication` durably changed queued targets to `DISPATCHING` before network I/O. The runner resolved scoped Ozon credentials, rechecked readiness and invoked `ozon.Client.UpdateStocks` with frozen quantities. It recorded success, failure or uncertainty per target via `FinishStockTarget`. An operator could request `Reconcile`, which used a read-only Ozon stock query; matching reported quantities became `CONFIRMED_EFFECTIVE` and disabled automatic publication, followed by a new review and a fresh, operation-bound competing-writer attestation before resumption.

Former triggers were: explicit enable, a later eligible imported change while the policy remained enabled, worker start/restart with an existing queued job or enabled policy, and background reevaluation. Worker restart could mark old dispatches UNKNOWN; it did not intentionally put DISPATCHING back into QUEUED. Retrying an identical enable API intent returned the ledger result and was not intended to create another operation. The application did not deliberately retry a marketplace POST; the standard transport had subtler connection-level behavior discussed below. Browser refresh and an idempotent retry could recover a submitted operation, not prove marketplace execution.

After containment, the same preview/ledger/worker path can be exercised only against an explicitly configured loopback simulator. Normal enable returns `STOCK_PUBLICATION_DISABLED`; a production Ozon client has stock writes disabled. `Reconcile` remains a separately requested, read-only provider call and can contact Ozon if an operator invokes it with existing credentials. The UI reports the publication hold and retains the ability to disable an existing policy and inspect an uncertain result. The API reports availability separately from the persisted `enabled` intent: an existing enabled row is not proof of a running or healthy publisher.

## Quantity and concrete counterexamples

`commitment.Evaluate` uses arbitrary-precision nonnegative whole numbers and computes `max(0, physical warehouse stock − source reserve − operator supplied unreflected obligations − operator supplied unseen-reduction bound − operator supplied safety stock)`. The result must also fit 0…2,147,483,647 for the adapter. There is no rounding or unit conversion; `"1.0"` is accepted as a whole number, fractional or negative values are blocked. Missing fields do not become zero. A physically observed zero with zero deductions publishes a synthetic zero. The stock rows are warehouse-specific, not aggregate stock; they are not by themselves an independent cross-market reserve ledger.

Examples checked in PostgreSQL/tests:

- Physical 10, reserve 1, unreflected 0, unseen bound 0 and safety 1 yield 8. Missing unreflected obligations must not yield 9; it blocks. Physical 0 plus explicit zero deductions yields 0.
- An Ozon reserve of −1 was previously accepted as a present stock row; it now blocks. No assumption is made that `present`, `reserved` and `free_stock` have a particular arithmetic relation because that relation was not independently verified here.
- A product aggregate and its child variant could previously each map to a different Ozon offer and both expose 10 units of the same physical pool. Known parent/variant relations and exact same-item mappings now block. Missing parent data, kits and unregistered external channels remain residual unverified exposure.
- Traversal A starts before B, B commits, then A commits a different fingerprint. A received a larger ID and recent finish time, so the previous latest-by-ID query could use the older traversal as fresh. The audit guard blocks both MoySklad and Ozon when the latest inserted eligible traversal started earlier than an already persisted one; a genuinely new complete import is needed. Equal/overlapping reads and source-side consistency still depend on an operator attestation, not a provider watermark.
- Reusing an identical eligible import fingerprint does not create a new batch or refresh its original observation timestamp. A new equal-content import before the registration boundary can legitimately be persisted separately under the existing scope rule; this does not establish upstream transaction ordering. A proof recorded midway through an import can be later than the actual stock row despite preceding batch completion; this now blocks publication.

## Findings and corrections

Severity count: **6 CRITICAL, 3 HIGH, 2 MEDIUM, 0 LOW**. The count groups related response-parser issues into H1. Scenarios below refer to the baseline unless stated otherwise.

**C1 — No deployment-level write gate.** `cmd/worker/main.go:run`, `internal/stocksync/runner.go:RunNext`, `internal/console/stock_sync.go:mutate` and `internal/infrastructure/ozon/stock_update.go:UpdateStocks` allowed a UI enable or an already enabled policy to lead to the official host without separate trusted deployment opt-in. Invariant: a front-end request or restart must not enable a marketplace write by default. Correction: explicit default-off configuration, API guard, no-op disabled runner and adapter-level literal-loopback-only write allowlist; real writes are currently disabled even with the flag. Tests `TestStockPublicationRequiresExplicitLoopbackSimulator`, `TestStockWritesRequireExplicitLoopbackOptIn`, `TestStockPublicationDeploymentGateCannotBeBypassedByEnableRequest` and `TestStockPublicationDisabledWorkerDoesNotClaimPreviouslyEnabledPolicy` cover configuration, client, API and old policies. Remaining uncertainty: old deployed binaries bypass the new guard; stop them all.

**C2 — A stale claimed worker could write after recovery.** `internal/postgres/stock_publication.go:StockPublicationCanDispatch` rechecked evidence and enabled state but did not compare the saved target state to its old in-memory DISPATCHING claim. A paused worker could resume after another worker marked it UNKNOWN and send. Invariant: a lost claim must not authorize a new request. Correction: recheck each target's scoped persisted state and frozen identity; a recovered UNKNOWN claim now fails the check. `tests/integration/stock_publication_test.go:TestStockPublicationRejectsRecoveredStaleWorkerClaim` reproduces the prior scenario. **Unresolved critical boundary:** another process can disable, recover or change evidence after this last check and before the HTTP request physically starts; a repeatable-read snapshot and a database transaction do not fence Ozon. The real adapter is held closed. No claim of exactly-once or full stale-worker exclusion across this gap is made.

**C3 — Historical mappings were not matched against current catalog identity/type.** `internal/postgres/stock_sync.go:stockSyncReview` and `internal/postgres/stock_commitment.go:loadStockMappings` checked a prior product/warehouse mapping, while `internal/postgres/stock_commitment.go:loadStockObservations` selected an Ozon stock row primarily by product and warehouse IDs. An offer/SKU change, archived product or warehouse changing to rFBS could leave a historical mapping apparently usable. Invariant: the current product, offer, SKU, source entity and FBS warehouse must match the frozen mapping. Correction: exact same-batch identity and FBS checks plus matching the current SKU to the import referenced by the confirmed mapping; missing values block. `tests/integration/stock_publication_test.go:TestStockPublicationRequiresCurrentCatalogIdentity` changes offer, SKU in one or both observations, archive status, warehouse type and source item. Provider-level identifier reuse/change rules are not independently proved.

**C4 — Product/variant double exposure.** `internal/postgres/stock_commitment.go:loadStockMappings` detected another exact `(kind,item)` mapping but not a mapped parent product and its mapped child variant. Both could be calculated from overlapping stock. Invariant: one physical pool cannot fund two independent targets. Correction: check known current source parent/variant relations across mappings and block both. `tests/integration/stock_publication_test.go:TestStockPublicationBlocksProductAndVariantSharedPool` uses 10 units in both rows. This is not a general bundle allocator: missing parent relationships, kits and unknown external exposures remain unresolved; real writes stay disabled.

**C5 — Older traversal could become latest and artificially fresh.** `internal/postgres/import.go:saveInventoryImportTx` and `internal/postgres/ozon_import.go:saveOzonImportTx` serialize persistence but do not require traversal start order; `internal/postgres/stock_commitment.go:loadStockObservations` chose the highest ID and local finish time. A late-finishing older traversal could be selected after a newer one. Invariant: a known earlier-started snapshot must not overwrite a newer one for publication. Correction: preview/reevaluation block when a later ID has an earlier start than a prior eligible batch. `tests/integration/stock_publication_test.go:TestStockPublicationRejectsOutOfOrderImports` and `TestStockPublicationReusedBatchDoesNotRefreshObservationTime` cover both providers and original batch reuse. Overlapping traversal internals and clock/source freshness are not independently resolved.

**C6 — A batch finish timestamp was mistaken for the time of every source read.** `internal/postgres/stock_sync.go:stockSyncReview`, `internal/postgres/stock_commitment.go:loadStockObservations` and `internal/commitment/calculator.go:Evaluate` accepted dynamic operator proof `as_of` up to the batch `finished_at`. For example, an uncertain write is read back at 12:01:00; a new source traversal read stock at 12:00:59, the operator attested no old writer at 12:01:01, and the traversal finished at 12:01:02. The old check could treat the stock row as fresh after settlement even though it was read before. Likewise, an old multi-minute traversal finishing now appeared fresh. Invariant: dynamic assertions must predate the entire source traversal, and old-started traversals must not be made fresh by a recent finish. Correction at the publication boundary: all attested dynamic proofs (other than static unit equivalence) must be no later than source `started_at`; both MoySklad and Ozon traversals must start within 15 minutes, and preview expiry is capped at their respective start plus 15 minutes. New source traversal must start after the operation-bound settlement assertion. Equal start timestamps for distinct batches also block because ordering cannot be established. `TestStockPublicationRejectsProofAfterSourceTraversalStarted`, `TestStockPublicationRejectsLongRunningTraversalEvenIfRecentlyFinished`, `TestStockPublicationReviewExpiresWhenMarketplaceTraversalAgesOut` and `TestStockPublicationRejectsIdenticalStartTimesForDifferentBatches` cover these cases. The shared calculator by itself still uses finish-time evidence; it cannot authorize publication without the new boundary checks. Source-provided transactional timestamps and clock synchronization remain unverified.

**H1 — Ambiguous HTTP/partial responses were made definite failures.** `internal/infrastructure/ozon/stock_update.go:UpdateStocks` mapped 400/401/403/404/409/429 and `updated:false` errors to FAILED without a verified guarantee that no asynchronous effect occurred; malformed duplicate or unexpected entries could be skipped alongside a valid success. A later changed import could then remove the pending fence and enqueue again. Invariant: absence of an authoritative per-target outcome must remain uncertain. Correction: every non-2xx, per-target error, malformed, duplicate or unexpected entry is UNKNOWN; valid per-target successes are retained. Tests `TestStockWriteHTTPErrorRemainsUnknownAfterPossibleApplication`, `TestStockWriteTimeoutWhileServerContinuesIsUnknown`, `TestStockPublicationLostResponseNeverReissuesRegardlessOfEffect` and `TestStockPublicationPartialErrorKeepsUncertainTargetFenced` exercise these cases. Exact Ozon semantics still need primary contract confirmation.

**H2 — Invalid observed marketplace numbers did not block readiness.** `internal/postgres/stock_sync.go:stockSyncReview` checked Ozon row existence/freshness but not negative `present`, `reserved` or `free_stock`. An operator attestation could mask inconsistent observed evidence. Invariant: known invalid quantities cannot become READY. Correction: require all three values present and nonnegative, without inventing a provider-specific arithmetic relation. `tests/integration/stock_publication_test.go:TestStockPublicationRejectsInvalidMarketplaceNumbers` covers each negative field; negative/fractional/overflow source values and missing reservation remain blocked by the calculator.

**H3 — Readback could settle an incomplete page.** `internal/infrastructure/ozon/stock_update.go:ReadStockQuantity` accepted a matching first-page row without checking `has_next`; a later page could contain duplicate or conflicting observations. Invariant: incomplete or ambiguous readback cannot release an unknown target. Correction: require a known complete one-page response; duplicate/missing pagination remains unavailable. `internal/infrastructure/ozon/stock_update_test.go:TestStockReadbackRejectsIncompleteOrAmbiguousPages` covers `has_next=true`, absent pagination status and duplicate records. A complete response can still be stale or coincidentally match.

**M1 — Readback copy overclaimed current state.** `web/src/StockSyncControls.tsx:StockSyncControls` presented a returned matching quantity with no freshness timestamp, but said the current Ozon stock matched. Correction: UI now says Ozon returned a matching value and explicitly says freshness and causal completion are unproved. `CONFIRMED_EFFECTIVE` is a legacy technical state label for a reported match, not proof of application.

**M2 — Configuration state was not worker health or deployment capability.** `web/src/Integrations.tsx:Integrations` and `web/src/StockSyncControls.tsx:StockSyncControls` could present an enabled policy and an old successful operation as an active synchronization even if no publisher could run. Correction: the API exposes the hard hold and the UI displays it, refuses enabling and does not mark the setup step complete. A general worker heartbeat/liveness indicator remains outside this audit; do not equate persisted enabled intent with operational delivery.

## Concurrency, unknown outcomes and limitations

The target partial unique index fences `(ozon_account, product_id, warehouse_id)` across scopes while QUEUED, DISPATCHING or UNKNOWN. Transactions use scope/import/mapping advisory locks and the per-account dispatch clock; concurrent tests produce one queued operation and one claim. A DISPATCHING task is not reclaimed for retry after a worker crash: after timeout it becomes UNKNOWN. The state check now rejects an already-recovered old claim, but a pause **after** that check is still an unavoidable software race without an external fencing primitive.

Disable cancels queued work; if an HTTP request has begun, `STOPPING` is accurate and the remote request can still complete. Mapping, credentials, source evidence and policy are revalidated before I/O, but can change in the gap after that check. No DB transaction is held over HTTP. Outbound batches are bounded to 100 targets; the implementation imposes one second between account requests and 30 seconds per target, using database state and process-provided timestamps. Clock skew, server restarts, a split deployment, failover and other writers outside STYK can invalidate rate/order assumptions. The simulator adapter disables connection reuse, does not follow redirects, and has no application-level write retry; this does not establish remote exactly-once delivery.

Synthetic tests model both applied and rejected requests with a lost response, a client timeout while the server continues, an actual synthetic worker subprocess killed after dispatch, a closed database after an HTTP effect but before terminal persistence, partial results, a coincidental matching readback, a mismatching readback caused by another writer, and disable racing an in-flight request. These verify retained UNKNOWN/partial state and no automatic reissue on the tested paths. They do **not** establish remote server cancellation, timestamp accuracy, actual process/OS scheduling behavior, provider proxy behavior or whether Ozon applies updates asynchronously. A matching response may be stale or coincidental. A manual attestation of no outstanding writer is an assertion, not a provider-issued proof.

## Credential security and isolation

`credentials.Vault` uses AES-256-GCM, random 96-bit nonces from `crypto/rand`, a separately supplied base64-decoded 32-byte master key and AAD covering version, tenant, provider, account and revision. The ciphertext contains nonce+ciphertext+tag; authentication/decryption errors fail closed. A separate derived HMAC-SHA256 key protects idempotency digests. Database records store ciphertext and metadata, not secret bodies; metadata API omits ciphertext/digests. Save probes a fixed official host before an atomic scoped registration/credential transaction; an Ozon key proves access to the supplied client ID, not ownership; MoySklad identity checks the returned account. Disabled stored credentials override environment fallback. Resolver enforces exact registered environment fallback and exact scoped stored records.

Provider/import and publication errors are sanitized before worker logging; response parsing and tests use synthetic values. The browser password field is not rendered in HTML attributes or browser storage; an exact request body including the secret remains in React memory while an uncertain save needs recovery. Same-origin XSS, malicious extensions, browser debugging, crash dumps and a compromised operator process can read it. No production tenant authentication, isolated secret manager or complete process-memory zeroization exists. Arbitrary free-text proof provenance is stored durably: operators must not place credentials or customer data there. A master-key rotation/reencryption protocol is not implemented; changing or losing the key makes old ciphertext and request-digest replay unusable. Backup and separate master-key custody are mandatory. These are deployment limitations, not claims of cross-tenant authorization.

## Ozon contract: verified versus unverified

The official [stock-management recommendations](https://dev.ozon.ru/start/299-Rekomendatsii-po-upravleniiu-ostatkami-v-Seller-API/) describe `/v2/products/stocks`, persisted-before-send changes, up to 100 product–warehouse pairs, 80 requests/minute per seller and 30 seconds per pair as published in 2024. The official [FAQ](https://dev.ozon.ru/start/257-FAQ-spravochnik-oshibok-i-sposoby-ikh-resheniia) explains that submitted free stock is added to reserved stock. Ozon's [retirement notice](https://dev.ozon.ru/news/585-Seller-API-Otkliuchenie-metoda-v1-product-import-stocks/) points away from `/v1/product/import/stocks`. Ozon’s [integration case](https://dev.ozon.ru/case/284-Keis-razrabotki-plagina-Ozon-Seller-WooCommerce-Opyt-Woodev/) describes using `product_id`, `warehouse_id` and a stock quantity. These pages support the endpoint, warehouse dimension and general reserve warning; they do not establish all current schemas or operational guarantees.

The current [interactive Seller API operation](https://docs.ozon.ru/api/seller/#operation/ProductAPI_ProductsStocksV2) returned no extractable schema in this audit environment. The builder's `Client-Id`/`Api-Key`, `stocks[]`, `product_id`, `warehouse_id` and `stock` fields and the parser's `result[]`, `updated`, `errors` and identifier semantics are **implementation assumptions exercised against synthetic fixtures**, not a fully verified present-day contract. In particular, precedence of product versus offer identifiers, exact per-target failure finality, omitted/duplicate fields, asynchronous application, readback pagination/freshness, ordering, retry/idempotency and current rate limits require a directly accessible official specification and controlled provider validation. No live marketplace endpoint was contacted.

## Tests and conditions before live use

Passed: `gofmt`/`make lint` (including vet), `make test`, `go test -race ./...`, `make build`, migration of a fresh dedicated local PostgreSQL database and the full PostgreSQL integration suite. The targeted publication suite passed 28 top-level cases under `-race`; its subprocess-only helper is intentionally skipped in the parent process. Three credential database integration cases passed under `-race`. Publication-specific race tests cover concurrent claims/intent, exact scope, target fences, stale/expired evidence, rotated credentials, mapping revision/identity, unknown/partial outcomes, lost responses, DB loss, incomplete readback, old snapshots, duplicate stock pools, default-off controls and HTTP enable/replay/disable against synthetic fixtures. Credential tests cover AEAD tampering, scope/revision binding, nonce generation, immutable idempotency and local-only HTTP/worker fixtures. Frontend lint, typecheck/build and 116 unit tests passed. Both existing import browser regressions passed against synthetic providers. Twenty-one Playwright UI regressions passed, including a previously enabled policy under the deployment hold. No test contacted a live marketplace. These results do not prove production safety.

Before any live use, at minimum: independently confirm Ozon's current complete write/readback contract and semantics; establish a provider-side idempotency/conditional-write or an operational protocol that provably excludes stale/in-flight writers before fence release; prove source snapshot ordering and a complete reservation/order/exposure model; address parent/variant, bundle and cross-channel allocation with authoritative evidence; implement real tenant authentication, authorization, master-key rotation and operational monitoring; assess clocks/rate limits; and conduct controlled tests in an appropriately isolated seller environment with explicit authorization. The real-host write hold must not be removed just because the deployment flag is present or synthetic tests pass.
