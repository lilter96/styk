## Ozon creation investigation

Ozon's live category tree, category attributes and dictionaries were read successfully. The chosen conceptual item was an unbranded paper sticker; its prospective category and type were returned by the account. The live dictionary included a matching description for printed self-adhesive paper labels and a `no brand` value. Eleven sticker, label and other simple stationery types were examined; all eleven reported the customs-classification attribute `22232` and mandatory-marking attribute `23536` as required. Ozon's own notices describe [the required customs-code field](https://dev.ozon.ru/news/690-Seller-API-Atribut-22232-stal-obiazatelnym-dlia-zapolneniia-dlia-mnozhestva-kategorii/) and [the boolean marking field](https://dev.ozon.ru/news/777-Izmenenie-validatsii-atributa-23536-Nuzhen-kod-markirovki-v-Seller-API/). The dictionary match is not itself proof of the legal classification or marking treatment of a real item. Ozon advises checking the code against product documentation or the manufacturer, importer or supplier; the [official marking checker](https://честныйзнак.рф/checking_codes/) returned HTTP 403 in this environment. Mandatory marking and ordinary product identification were not conflated.

The seller-info read returned a tax-system field, but no explicit VAT-rate field. A bounded read of nine active catalog price rows returned three distinct VAT values. Those values do not establish the applicable VAT for this synthetic offer. The catalog's 33 product names and the available description/model attributes were scanned for explicit test-only markers; none was identified by this bounded scan. Three offer IDs containing an ambiguous `ATEST` substring were not treated as proof of test ownership. None of the nine active products had the selected exact sticker category and type. These observations do not prove that no designated test offer exists outside the fields or permissions examined, and no unrelated offer was used or duplicated.

The official [product-import guidance](https://dev.ozon.ru/start/294-Avtomaticheskii-import-i-obnovlenie-tovarov-v-Seller-API/) describes mandatory category, attributes, product content, image, price and VAT; its later [type-ID guidance](https://dev.ozon.ru/start/334-Ispolzovanie-polia-type-id-v-Seller-API/) describes `type_id`. Product import is asynchronous, and a task submission would not by itself establish moderation, SKU assignment, FBS eligibility or an active offer. The current complete interactive request schema and official Swagger could not be retrieved directly: the browser received HTTP 403 and the documentation fetcher could not return the oversized Swagger document. An independent mirror was consulted for read-only discovery, not treated as current authoritative proof for a write.

**BLOCKED:** No product submission was made because the applicable seller VAT and marking declaration for the proposed fixture were not reliably established, and the full current write schema was unavailable. The owner authorized arbitrary synthetic fixture content, but the account-specific tax and regulatory declarations remained unverified real-provider fields. Account permission to create a product, moderation, archive state, SKU assignment and propagation are therefore **NOT_TESTED**, not provider failures. The public test image exists, but image availability does not resolve those other conditions.
