# Ozon live read-only contract validation

The account owner confirmed ownership and authorized bounded read-only diagnostics for the locally configured seller account. No account identifiers, credentials, raw responses or customer details were recorded here. The local read-only client used one attempt per request, a 10-second request timeout, bounded overall contexts, one-second rate limiting and disabled redirects. No Ozon writes or database imports occurred.

Six live requests were made: two `POST /v3/product/list`, two `POST /v2/warehouse/list`, one `POST /v2/product/info/stocks-by-warehouse/fbs`, and one `POST /v4/posting/fbs/list`. The product and warehouse follow-up requests checked field presence. The stock request used one offer from the product response. The posting request covered the preceding 24 hours, with limit one and optional analytics, financial, legal and barcode data disabled. `POST /v3/posting/fbs/get` was not called because the posting list was empty.

| Probe | Result | Evidence and limits |
| --- | --- | --- |
| Authentication and products | PASS | Both product requests succeeded; one row contained `product_id`, `offer_id`, `sku` and `archived`; `result.items`, `last_id` and `total_items` were present. This does not establish archived-item behavior or a complete traversal. |
| Warehouses | PASS | One row exposed `warehouse_id`, `is_rfbs`, `warehouse_type` and `status`; the response included `cursor` and `has_next`, with continuation indicated. The next page and empty-list behavior were not checked. |
| Warehouse stock | WARN | The request succeeded with `products`, `cursor` and `has_next`, but returned no stock rows for the selected offer. Quantity semantics, populated fields and warehouse linkage remain unverified; absence is not zero. |
| FBS posting list | WARN | The request succeeded with top-level `postings`, `cursor` and `has_next` and no legacy `result` wrapper. The selected 24-hour window was empty; populated identity, status and timestamp fields remain unverified. |
| Posting detail | NOT_CHECKED | No posting was returned in the bounded window. |

No response-shape discrepancy was observed in the fields actually returned. Empty responses cannot verify the stock-row or posting-detail contracts. There were no observed authentication errors, 429 responses or server errors, so those live error shapes were not verified. No code fix was justified by these probes. Full catalog and historical imports were not run: the existing catalog importer traverses the account rather than accepting a one-product scope. Integration Doctor was not run against live imports; no Ozon observations or mappings were fabricated.

The [official Ozon replacement notice](https://dev.ozon.ru/news/648-Izmeneniia-v-metodakh-Seller-API/) documents retirement of earlier warehouse and stock methods. The interactive official API documentation was not accessible for complete independent contract review; the existing implementation also relies on a [published OpenAPI snapshot](https://github.com/MissiaL/ozon-api/blob/main/references/ozon-seller-openapi.json), which is secondary evidence and may lag Ozon. Successful requests verify only their observed shapes and permissions, not all documented behaviors. A populated FBS stock row and a nonempty, separately authorized posting window are needed to validate their fields and the detail endpoint. Pagination continuation, archived products, full permissions and real cross-system mappings also remain unverified. Successful responses do not establish safe stock synchronization.
