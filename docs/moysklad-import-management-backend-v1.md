# Durable MoySklad catalog import backend V1

`MOYSKLAD_CATALOG_IMPORT` extends the existing durable import API, outbox queue and worker. It uses the existing MoySklad catalog reader and canonical fingerprint, and the same persistence inserts as the trusted CLI. It reads products, variants with parent identities, warehouses, aggregate stock and warehouse stock. It never reads customer orders or creates external entities. This milestone adds no React action.

## API and configuration

Configure `MOYSKLAD_ACCOUNT_ID` and `MOYSKLAD_TOKEN` locally in both the API and worker environments. Register the source account under the intended tenant through the existing trusted administrative mechanism, then start `go run ./cmd/api` and `go run ./cmd/worker`. Restart processes after configuration changes. A single current worker can process both providers and mock tasks; missing or invalid provider settings leave that provider's operations queued. Stop older workers before deploying the new task type. Host restrictions are unchanged: production constructors target only the official HTTPS provider hosts and the MoySklad client allowlists GET read endpoints. No token is stored in the database, returned to the browser or accepted from a request.

Authenticated loopback `POST /api/imports`, with the existing required Origin and JSON checks, accepts:

```json
{"tenant":"local-tenant","moysklad_account":"configured-account","operation_type":"MOYSKLAD_CATALOG_IMPORT","idempotency_key":"catalog-intent-1","acknowledge":true}
```

The server requires the selected account to match its local configuration and a registered tenant/provider/account. A supplied account ID is not ownership evidence. `GET /api/imports?tenant=...&moysklad_account=...&limit=20&offset=0` lists bounded history (limit 1–50, offset 0–10,000). `GET /api/imports/{id}` uses the same tenant/account query. Cancellation uses `POST /api/imports/{id}/cancel` with `{ "tenant":"...", "moysklad_account":"...", "acknowledge":true }`. Only queued tasks can be cancelled. A late cancellation never changes a running or succeeded operation.

Existing Ozon requests continue to use `ozon_account`; selecting both account fields is rejected. Old Ozon idempotency fingerprints remain compatible. Submission keys remain unique within a tenant and bound to operation type, exact account and frozen limits; a type change is a content conflict. Identical retries return the original operation, including after a lost response. PostgreSQL enforces one active catalog task per tenant, **provider** and account. Identical account text in different provider namespaces does not cause an active-task conflict or allow cross-provider inspection.

## Execution limits and observations

Defaults and maximum accepted settings are 100 logical requests, 100 actual HTTP attempts, 100 pages, 1,000 products, 1,000 variants, 1,000 warehouses, 10,000 aggregate observations, 10,000 warehouse observations, 4 MiB per response, three minutes per attempt and ten seconds for persistence. A complete optional `limits` object can lower these values; it uses the existing fields plus `variants` and `warehouse_observations`. `observations` counts aggregate rows for MoySklad. The existing larger fixed client ceilings remain in effect as additional safeguards. The manual CLI retains its prior fixed limits; durable execution adds stricter limits around the same reader.

A logical request is admitted once per page; retries consume the separate network-attempt budget. The bounded production transport disables connection reuse so Go cannot transparently replay a GET on a stale pooled connection outside this accounting. Pages, entities and nested warehouse rows cannot bypass their limits. Bodies are capped while reading, not after an unlimited allocation. Context cancellation and the attempt deadline cover rate-limit waits, pagination, retries, fingerprint validation and final persistence. The transaction timeout can end persistence sooner. No network request occurs inside the persistence transaction.

The worker respects stricter `MOYSKLAD_HTTP_TIMEOUT`, `MOYSKLAD_REQUEST_INTERVAL`, `MOYSKLAD_RETRY_BACKOFF`, `MOYSKLAD_MAX_RETRY_AFTER` and `MOYSKLAD_MAX_ATTEMPTS` settings. Requests default to 30 seconds, a minimum 400ms interval, up to three attempts and at most a minute of accepted rate-limit delay. Invalid settings disable claiming that provider. Existing Retry-After handling is preserved: standard Retry-After is seconds or an HTTP date, Lognex retry/reset values are milliseconds, and exhausted X-RateLimit-Remaining can defer subsequent requests. Authentication failures are not retried. Rate limiting is process-local, including relative to manual CLI imports.

Numbers remain source-specific decimal values. Aggregate stock, reserve, incoming, quantity and optional free stock remain distinct. Warehouse available quantity remains NULL because the selected report does not provide it. An absent row is unknown; an explicitly reported zero is zero. Source updated fields and local observation timestamps retain existing meanings. Completed traversal establishes neither exhaustive visibility nor an atomic source snapshot.

## Progress, persistence and recovery

The existing states are unchanged: QUEUED, RUNNING, SUCCEEDED, FAILED, CANCELLED and OUTCOME_UNKNOWN. MoySklad phases are READING_PRODUCTS, READING_VARIANTS, READING_WAREHOUSES, READING_AGGREGATE_STOCK, READING_WAREHOUSE_STOCK and PERSISTING, followed by a terminal phase. Counters are attempt-local and reset when reclaimed. Progress is persisted at phase changes and at most every two seconds at page boundaries. It is not committed inventory or a completion percentage.

The existing runner now dispatches the two catalog types through its shared lease renewal and completion path. Claiming is scoped to the worker's configured provider accounts. Lost renewal cancels traversal. Fenced persistence locks the task/claim, validates provider/account registration, takes the existing `moysklad:<account>` advisory lock and rechecks lease validity at terminal update. It commits source data, operation linkage and task success in one bounded transaction. A stale claim cannot commit or overwrite a new result. Manual and worker imports share the advisory lock and fingerprint rules. Incomplete traversal saves no completed batch and preserves previous imports.

Consecutive identical content may reuse the latest eligible batch (`batch_created=false`); new content creates a batch (`true`). Reuse does not refresh source or observation timestamps. Hidden pre-registration batches cannot be reused unless the registration explicitly includes history. Account/provider-scoped foreign keys and a deferred eligibility trigger reject unauthorized batch links. A privileged database owner bypassing these mechanisms remains outside the application guarantee.

A lost database COMMIT response is reconciled under the task lock using the durable task/operation/batch state. If reconciliation is unavailable, the outcome stays unresolved for lease recovery; no failure is asserted solely from the lost response. A crash before persistence can repeat read-only traversal. A committed success already includes task completion. These are fenced database guarantees, not exactly-once HTTP execution. Queued cancellation is supported; active cancellation, schedules and recurring imports are not.

## Migration and verification

Migration 22 extends the existing `ozon_import_operations` table without renaming it or rewriting operation history. The historical SQL name remains for compatibility. It generalizes provider/type, phase and resource constraints; adds a generated task provider and provider-scoped foreign key; replaces the active-task index with provider-aware uniqueness; and extends deferred batch/terminal consistency checks. Adding constraints, indexes and the generated stored column scans or rewrites the affected tables and takes PostgreSQL locks: stop workers and plan deployment. Down migration refuses to discard MoySklad operation history; an empty MoySklad history allows reverting the structural change. No production database was migrated during this task.

Synthetic tests cover both APIs, scoped submission, cancellation, idempotency, worker dispatch, paginated observations, explicit zero and NULL values, transport and response limits, rollback, timeout, lease renewal/loss/reclaim, manual-import concurrency, hidden-history exclusion and durable reconciliation after a proxy drops PostgreSQL's successful COMMIT response. Existing Ozon, mapping and mock-worker integration tests are also run. No live marketplace credentials or requests are used. The local shared operator session remains a trusted workspace boundary, not production tenant authentication or verified human identity.

Verification completed with `make lint` (including gofmt and vet), `make test`, `go test -race ./...`, `make build`, PostgreSQL integration tests and race-enabled integration tests. Fresh databases migrated through 22; migration 22 reverted and reapplied with no MoySklad history; upgrading a database with existing Ozon operations preserved those records unchanged; rollback with MoySklad history was rejected as intended. All provider responses were synthetic. Existing local imported databases were not used for these checks.
