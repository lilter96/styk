# Stock shadow mode V1

Stock shadow mode is a read-only inspection of the selected registered MoySklad and Ozon account pair. In Integrations, choose a workspace and accounts, then select **Проверить остатки**. The dialog shows confirmed product/warehouse pairs, observed warehouse physical stock and reserve, observed Ozon free stock, a candidate when the existing review can calculate one, and actionable reasons when it cannot. Product and warehouse names come from the selected imports; offer ID, SKU or scoped IDs are fallbacks. Variant parent identity is shown when the source import contains it. Account labels use configured names or the same numbered account labels as the integration page.

A candidate is an output of the existing `StockSyncStatus` → `stockSyncReview` → `commitment.Evaluate` path, subject to the existing per-target publication review checks. The UI does not calculate inventory; it subtracts the observed Ozon value only to display a difference. A candidate is not authorization to publish. Actual Ozon writes remain held closed at the API enable gate, worker and adapter. The shadow endpoint is a GET and does not create reviews, decisions, publication intents, outbox tasks, mapping confirmations or provider requests.

## Evidence and freshness

Observed quantities come from the selected, eligible persisted batches. Missing values remain unknown; zero is shown as zero. The original row and batch timestamps never change when identical content is reused. A separate, tenant/account-scoped successful durable import operation can establish that the selected batch's content was traversed again. Its attempt start is the conservative freshness boundary; its operation ID and completion time remain separate from the historical row timestamp. A later operation for a different batch does not refresh the selected batch. Neither the original nor repeated traversal is a provider watermark or proof of an atomic snapshot, and separate provider traversals are not simultaneous. Stale evidence blocks the existing review; technical details show original batch times, the latest completed traversal where available, and failed checks.

The authoritative status is evaluated in its existing database transaction; display names, batch timestamps and the uncertainty flag are then read separately. A concurrent change can therefore occur while the response is being assembled. Refresh to inspect newer evidence; this view is not a transaction fence or a guarantee about subsequent state.

Operator-entered obligations, unseen reductions, safety stock and proofs are assertions, not independent STYK verification. The shadow endpoint reuses attestations associated with the existing scoped setting; it does not collect, infer or renew them. Consequently, an account pair with no such evidence will normally show observations and blockers but no numeric candidate. A previously saved attestation can expire or become invalid after an import, mapping or credential change. The audit's unresolved ordering, allocation, ownership and remote-write risks still apply.

## Scope and tests

The authenticated local-operator API requires an exact tenant, registered MoySklad account and registered Ozon account. It returns only the existing bounded set of up to 100 mapped pairs for that scope; unmatched catalog products are handled via the product and warehouse mapping links. This local operator session is not production multi-tenant authentication. No new credentials or raw provider responses are exposed.

`TestStockShadowProjectionBoundaries`, `TestStockShadowRejectsParentVariantOverlap` and `TestStockShadowStaleReusedAndUnknown` use disposable PostgreSQL and the actual authenticated API. They check explicit zero versus missing observations, missing reserve, invalid quantities, shared product/variant pools, original batch timestamps, staleness, expired attestations, unknown writes and cross-tenant/account isolation. Candidate values are compared with the authoritative review. Existing publication tests cover additional calculator, concurrency and fencing cases.

`TestStockShadowBrowser` starts the real Go console, current Vite application and synthetic local database fixtures; Playwright logs in, selects the account pair, inspects both a valid calculated candidate and a missing-data target, opens details, visits product mapping, returns, refreshes and checks the scope. The fixture has a disabled, pre-existing synthetic review and no publication task. Before and after the browser journey the test compares publication intents, operations, mapping confirmation audits, stock decisions, reviews and outbox entries. A synthetic transport guard rejects external provider traffic, and the browser asserts that no stock-write or publication-mutation request was made. Screenshots cover desktop and mobile overview, missing-data and expanded-details states.

Run the browser test with `STYK_SHADOW_BROWSER_E2E=1` and `TEST_DATABASE_URL` pointing to a migrated, disposable local database whose name contains `styk_stock_publication_v1_test`. All fixtures are synthetic. Shadow mode does not establish production readiness or lift the [stock publication safety hold](stock-publication-safety-audit.md).
