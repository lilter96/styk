# LIVE-дефекты и ограничения — 2026-11-07

## Ozon: отрицательный идентификатор перевозчика скрывал отправление

Реальные `POST /v3/posting/fbs/get` вернули HTTP 200 для двух исторических
Express-отправлений первого аккаунта. В обоих ответах
`delivery_method.tpl_provider_id` равен `-2`. Общий декодер идентификаторов
принимал только неотрицательные цифры, поэтому вся карточка завершалась
`POSTING_SCHEMA_DRIFT` / `invalid Ozon order response`.

Причина подтверждена изоляцией ответа в памяти: удаление только
`delivery_method` устраняло ошибку; остальные факты сохранялись. Исходные
ответы с данными покупателей не сохранены в открытом виде. Официальная схема
определяет поле как `integer/int64`, без минимального значения. Значение `-2`
не документировано как разрешение на доставку или подтверждение перевозчика.

Исправление и повторный LIVE-readback регистрируются после выполнения.

## Финансовый источник: отсутствие отчёта не равно нулю

Для первого Ozon-аккаунта запросы `/v2/finance/realization` за август,
сентябрь и октябрь 2026 вернули HTTP 404. Это отсутствие доступного источника
для этих запросов; права на финансовые записи, нулевой отчёт и успешный импорт
из этого не следуют. STYK сохранил отказ и не выполнил финансовый POST.

## Исправления Ozon подтверждены повторным LIVE-read

Signed provider ID исправлен отдельным canonical signed-int64 декодером только
для `delivery_method.provider_id/tpl_provider_id`. Order/SKU/warehouse/method IDs
не расширены. Отрицательный provider ID сохраняется как наблюдение, не даёт
capability и не называется известным перевозчиком. Два исходно нечитавшихся
отправления `6b2c585f8a76`, `3c2c4ccecf6c` после исправления прочитаны успешно.
Синтетическая обезличенная fixture и tests проверяют отрицательный ID,
malformed/overflow/leading-zero, строгие остальные ID и отсутствие delivery grant.

## Финансы: реальный новый component ломал source preview

Второй Ozon-аккаунт вернул HTTP 200 с
`delivery_commission.pick_up_point_coinvestment`, которого нет в опубликованной
базовой схеме и прежнем allowlist. Из-за strict unknown-field gate нормальный
отчёт был полностью отклонён. Поле добавлено как **LIVE_OBSERVED_UNDOCUMENTED**,
с точным decimal/presence, без расширения остальных unknown-field допусков.
NULL/missing/zero различаются; значение участвует в source fingerprint. Native
planner и final preflight разрешают только явный ноль этого дополнительного
компонента. Ненулевое, отсутствующее или NULL требует ручной проверки.

Для старых сохранённых snapshots/preview/work отсутствие нового поля не меняет
serialized JSON/hash (`omitzero`); старый ещё не отправленный work всё равно
проходит **текущий** component gate перед записью. Уже отправленный UNKNOWN
сохраняет старую идентичность и read-only reconciliation, повторного POST нет.
После изменения реально прочитаны все семь доступных отчётов — 254 строки.
Два исходных HTTP200/parser failure за август и октябрь больше не воспроизводятся.

## Неподдержанные данные финансовых источников

В реальных источниках большинство `return_commission` — NULL; часть строк
содержит реальные returns/отсутствующие sale-компоненты. NULL не является
подтверждённым числом ноль. Все семь отчётов не проходят нынешнее sales-only
подмножество. Это ограничение **STYK**, а не утверждение, что Ozon или МойСклад
запрещают их импорт. Нет подходящего Commission/None договора и отдельной
согласованной бухгалтерской policy. Поэтому реальный commissionreportin не
создавался; фиктивный отчёт ради зелёного результата не использован.

## Диагностические запросы, которые не являются дефектами штатного importer

Дополнительный point-stock probe с `quantityMode=all` получил HTTP 412/code
1034: провайдер не поддержал этот параметр. После перехода на **существующий
штатный** запрос `report/stock/bystore?filter=stockMode=all&groupBy=variant`
получен HTTP 200, полный список из 33 строк и точные два пула. Исходные 412
оставлены в журнале; неизвестный остаток не превращался в ноль. Этот probe
находится в private acceptance helper, не в production importer.

Проба фильтра `entity/demand?filter=customerOrder=…` также получила HTTP 412/code
1034 на известном положительном и отдельном sparse parent. Такой фильтр не
внедрён: официальный перечень filterable references его не подтверждает.
Отсутствие `customerorder.demands` требует отдельного доказательства покрытия.

## Один неуспешный read application ingestor

Первый single-process проход прочитал native-points, затем updated-stream
завершился `MoySklad transport failure`. Повторён безопасный read; он прошёл.
Последующий конкурентный запуск двух экземпляров также прошёл, work/intents
не изменились. Причина первого сетевого отказа не доказана; поздний read-only
снимок не показал активных lease/locks/блокирующих PID. Этот отказ не скрыт и
не назван доказанным deadlock или успешно завершённым первым прогоном.


## МойСклад: sparse demands больше не блокирует автоматизацию без альтернативного proof

Реальные три parent опускают `demands`; unsupported customerOrder filter не
использован. Добавлено отдельное account-wide доказательство для автоматического
DemandCreate: fresh ALL до/после, два совпавших полных списка с проверкой каждой
страницы/account/reference, повторный неизменённый полный parent. При подготовке
записи повторяется свежий preflight; найденный draft тоже блокирует POST.
Raw provider observation, его revision и старый JSON/UNKNOWN readback сохранены.
Неполнота, ошибка, ограниченные права, изменившийся parent/список и исчерпание
обычных budgets остаются UNKNOWN coverage. Три реальных missing parent успешно
проверены. [Точная реализация, доказательства и TOCTOU](demand-coverage.md).

Независимый review выявил и устранил ошибку времени в новом bridge: финальная
проверка proof использует часы после внешнего I/O. Дополнительная HTTP/PG/race
регрессия имитирует реальную задержку, сохраняет missing/NULL header и проверяет
одну запись/restart/readback; поздний foreign draft даёт 0 POST. Это контрактное
доказательство worker-пути, не имитация реального физического handoff.
