# Durable Ozon catalog import operations V1

This is a local, authenticated operator API and a read-only worker operation. It does not provide production tenant authorization, scheduling, a frontend import screen, order synchronization or marketplace writes. `OZON_CATALOG_IMPORT` uses the existing bounded catalog traversal: product lists for `ALL` and `ARCHIVED`, warehouse listing and FBS stock observations. A completed traversal is not exhaustive account visibility or a point-in-time source snapshot; missing rows are unknown.

## API and ownership

Configure `OZON_CLIENT_ID` and `OZON_API_KEY` for both the API and its matching worker, and register the Ozon account to the chosen tenant using the existing trusted administrative mechanism. The API and worker must each be restarted after configuration changes. The local shared operator session grants administrative access to the workspace; tenant/account checks are database scoping, not individual user authorization. The account ID is not an API key. The API never accepts a token or API key from the browser or stores one in an operation.

Authenticated local `POST /api/imports` requires the configured Origin, JSON and explicit acknowledgement. Example body:

```json
{"tenant":"local-tenant","ozon_account":"configured-account","operation_type":"OZON_CATALOG_IMPORT","idempotency_key":"operator-intent-1","acknowledge":true}
```

The key is 1–128 ASCII letters, digits, `.`, `_`, `:`, or `-`. A caller may optionally provide a complete `limits` object using the field names returned by the API; values must be positive and cannot exceed the defaults below. The server validates the registration and requires the selected account to match its configured Ozon client ID. A successful connection test or account identifier does not prove marketplace ownership or full permissions. No import starts until this explicit request is accepted.

`GET /api/imports?tenant=...&ozon_account=...&limit=20&offset=0` lists only the registered scope; limit is at most 50 and offset at most 10,000. `GET /api/imports/{id}?tenant=...&ozon_account=...` inspects one operation. `POST /api/imports/{id}/cancel` accepts JSON `{ "tenant": "...", "ozon_account": "...", "acknowledge": true }` and cancels only a queued operation. A running or terminal operation returns `CANCELLATION_UNAVAILABLE`; active cancellation is not implemented. A late cancellation never overwrites a committed success.

The idempotency key is unique within a tenant and bound to the selected account, import type and frozen limits. An identical retry returns the existing operation; different content returns `IDEMPOTENCY_CONFLICT`. Submission and the outbox task commit together. A lost submission response may be retried with the same key. PostgreSQL also enforces at most one pending/running catalog task for the tenant and account; a different key receives `IMPORT_ALREADY_ACTIVE`. A terminal failure can be retried by explicitly submitting a new key. Authenticated local sessions share the trusted operator boundary; all reads and writes still require the exact registered tenant/account scope.

## Execution and recovery

Operations use the existing `outbox_tasks` queue. The worker claims with a new token and lease; only a worker configured for the matching Ozon account can claim that import. Mock jobs remain independently claimable. A missing or invalid worker configuration leaves the import queued for a matching worker. Distinct accounts can be handled by separate workers. The worker's client uses the existing limiter; it respects stricter `OZON_REQUEST_INTERVAL`, `OZON_HTTP_TIMEOUT`, `OZON_RETRY_BACKOFF`, `OZON_MAX_RETRY_AFTER` and `OZON_MAX_ATTEMPTS` settings within its conservative caps. Rate limiting is per process, not coordinated between processes or manual CLI imports.

Operator-facing states are `QUEUED`, `RUNNING`, `SUCCEEDED`, `FAILED`, `CANCELLED` and `OUTCOME_UNKNOWN`. The latter is a conservative read-time indication when a persistence-phase lease has expired; it does not assert that a commit succeeded or failed. Phases are `QUEUED`, `READING_PRODUCTS`, `READING_WAREHOUSES`, `READING_STOCK`, `PERSISTING` and terminal phases. Counters are attempt-local: logical requests, network attempts and page attempts; successful JSON responses and validated pages; products, warehouses and stock rows observed. Progress is stored at phase transitions and at most every two seconds at page boundaries, and is not a committed batch or a percentage. A reclaim resets attempt-local progress. Elapsed time is calculated from the current attempt start; source-event chronology remains unknown.

The default frozen limits are 100 logical requests, 100 HTTP attempts, 100 pages, 1,000 products, 1,000 warehouses, 10,000 stock observations, a 4 MiB response body, three minutes per attempt and ten seconds for the final database transaction. Smaller limits can be requested. The overall attempt deadline covers traversal, validation and persistence; the transaction timeout may end it sooner. A limit produces `LIMIT_REACHED` and a resource, without a partial batch. Other safe outcomes distinguish `API_FAILURE`, `INVALID_RESPONSE`, `PERSISTENCE_FAILURE`, `CONFIGURATION_UNAVAILABLE`, `CANCELLED` and `LEASE_EXHAUSTED`. Client errors and raw source payloads are not stored.

During traversal the worker renews the lease and cancels its work if renewal fails. Before persistence it stops the renewal goroutine, renews once, then locks and rechecks the exact task/claim/lease in a bounded transaction. No external HTTP call occurs in that transaction. The transaction writes the completed source batch, its scoped operation link and task success together; deferred database checks reject a successful task without its completed batch. A worker whose claim has expired or been replaced cannot update progress, save a batch or finish the task. The last attempt's expired lease is terminal. Repeated read-only traversal after a crash is possible; it is not an exactly-once external operation.

If the database commit response is lost, the worker reconciles persisted task and batch state while locking the task row; it does not blindly mark failure. If the database is unavailable, the task remains unresolved until lease recovery can inspect or reclaim it. A completed transaction already includes task success, so a claimant cannot create a second successful outcome for the same operation. Identical latest eligible source content may reuse its completed batch, indicated by `batch_created=false`. Historical imports hidden by the account registration cannot be reused; an import whose local start precedes the registration fails closed. Keep worker and PostgreSQL clocks synchronized. Separate manual CLI imports are outside this operation's active-task limit, though source persistence still uses the account advisory lock.

Migration 21 adds scoped references, immutable submission/terminal records, deferred task/batch consistency checks and account-specific indexes. Adding the scoped uniqueness constraint and indexes scans existing tables and takes PostgreSQL locks; plan deployment accordingly. Its down migration refuses to erase operation history. Stop or upgrade all older workers before submitting these tasks: older mock-only workers do not understand import task payloads. No new queue was introduced.

Integration tests use synthetic HTTP servers and a disposable database, including a local TCP proxy that drops the PostgreSQL COMMIT response after the server commits. No live marketplace credentials or requests are required.
