# Stock commitment engine: architecture and correctness review

Status: reviewed 28 October 2026; a limited read-only calculator is now implemented. No commitment ledger, allocation policy, Ozon stock writer, or reconciliation worker is implemented. V1 is a **read-only calculator and explanation**; it must not enqueue external writes. The inputs currently in STYK cannot, on their own, establish a safe positive publishable quantity. The numbers below are conditional examples, not production recommendations. See [invariants](stock-commitment-invariants.md) and the [test matrix](stock-commitment-test-matrix.md).

## Implemented read-only slice

The pure [calculator](../internal/commitment/calculator.go) checks scoped identities and mapping versions, evidence freshness, explicit proof provenance and validity windows, and exact nonnegative whole-piece arithmetic. Synthetic tests can supply all proof assertions and exercise `READY_CONDITIONAL`; these assertions are trusted test inputs, not verified external facts or a production proof source. Relevant proof intervals must cover the local baseline observation; the local timestamp itself is not a source-event timestamp. The PostgreSQL adapter supplies no unsupported cross-system proofs, and [migration 14](../migrations/00014_stock_commitment.sql) prohibits persisted `READY_CONDITIONAL`. Current imports therefore yield `UNKNOWN` or `BLOCKED`, with NULL quantity and an exposure warning.

The [administrative CLI](../cmd/stock-commitment/main.go) explicitly registers source/account ownership with provenance and calculates or inspects decisions. Earlier account-scoped imports are considered only when the operator explicitly attests their tenant ownership; otherwise imports must start after registration. Exact source/account identifiers are unique across tenants, but an operator must verify canonical identifiers and actual ownership; there is no authenticated tenant boundary. [Decision persistence](../internal/postgres/stock_commitment.go) uses a serializable transaction, the existing importer/mapping locks, immutable policy versions and scoped foreign keys for pool, source observations and confirmed mapping history. A frozen JSON snapshot preserves values even if a privileged user later edits a legacy source row. Database-owner privileges can bypass triggers. The V1 schema does not implement the proposed warehouse-binding or commitment ledger below; detected shared mappings block and unknown exclusivity remains a failed proof. See the [README](../README.md#read-only-stock-commitment-calculator) for commands and reason codes.

## Double-counting and missing-evidence analysis

No currently imported field proves when a particular Ozon order affects MoySklad. A source reserve total alone cannot establish overlap with a posting or an Ozon aggregate reserve. The following decisions are conservative; a hold is not an assertion that a source value is zero.

| Scenario | Evidence needed / V1 treatment |
| --- | --- |
| Posting exists, source does not reflect it | Count its obligation once **only** if a documented coverage and authoritative line-to-source non-reflection proof establishes its amount at the chosen baseline; otherwise unknown. A posting is not proof that the source is unchanged. |
| Posting is already in source reserve | Source reserve already reduces capacity; do not subtract the same units again. Require durable order/line-to-reservation provenance and compatible as-of evidence, not equal totals or timestamps. Partial reflection requires quantity-level evidence. |
| Reserve from another channel | Remains in source reserve and is not subtracted again merely because it is not an Ozon posting. External obligations not yet reflected in the reserve require separate coverage; origin cannot be inferred from `reserve`. |
| Source changes during a traversal | The transaction makes local persistence atomic, not source reads. A complete set of pages is not a common cut. Require a supported consistent baseline or a justified conservative bound for every intervening decrement, plus complete coverage; otherwise unknown. |
| Posting changes or is cancelled | Record another immutable observation. Release only the units proven no longer obligated **and** account for source reserve/stock changes. A cancellation can arrive after shipment or cover only a posting/line; reason and source ordering may be unknown. |
| Split order | Track posting identities and line composition, not one commitment per order. Do not count parent and child as independent obligations without documented split relations and quantities. Unresolved split is unknown. |
| Late cancellation | An older active observation or a later local import is not proof of the business order of events. Retain both; do not release or revive based on arrival order alone. |
| Stock stale, missing, incomplete, or negative | Missing is unknown, never zero. Expired data, unsupported fractional/negative values, or incomplete traversal block numeric output. A reported zero is a value only if the remaining gates hold. |
| Mapping changes after observation | Freeze confirmed mapping version at the calculation/evidence interpretation, preserve original external identity; re-evaluate when mappings change. Current correlation must not be presented as historical fact. If history cannot establish the affected pool, hold both possible pools. |
| Multiple seller accounts or marketplaces share a warehouse | Pairwise mapping constraints do not isolate physical stock. A common pool, all competing commitments and all outstanding channel exposures require one coordinated allocator; otherwise block. |
| Multiple offers for one source item | Same physical pool even within one account; do not give each offer the full available amount. V1 blocks shared targets. |
| Bundle/kit or multipack | A sale can consume multiple components or multiple units of one item; the current model has no verified bill of materials, pack conversion or allocation rules. V1 requires affirmative evidence of a simple one-to-one unit relationship and blocks unknown composition, bundles, kits and multipacks. |
| Earlier write has unknown outcome | Target may already advertise a different amount. Freeze automatic writes, retain exposure and reconcile; a local retry or lease expiry does not prove non-application. V1 issues no writes. |

## V1 domain and lifecycle

**Stock pool** = `(tenant, MoySklad connection, warehouse UUID, item kind, item ID, unit)`. It represents one physical resource, not a marketplace listing. **Channel target** = `(tenant, Ozon connection, Ozon warehouse, product ID, offer ID)` with SKU retained separately. V1 permits exactly one confirmed target per pool and one pool per target, a single managed seller account, and explicitly documented exclusive control over other channels and outside writes. Its warehouse binding is one-to-one across account pairs, not just within each pair. A confirmed product match is not proof of a one-unit sale: simple composition and unit conversion require affirmative evidence. Existing mapping uniqueness does not enforce these stronger assumptions.

**Evidence** is immutable: source stock observation; Ozon stock observation; posting observation and line multiset; actual source event ID/version when a contract supplies one; correction; allocation/provenance; and future external-operation evidence. Record original identifiers, account, local times and timestamp basis, traversal/window, and completeness. The system must not invent a source event from a local import ID or content hash. If source line IDs are absent, line ordinals are observation-local. If a posting has duplicate indistinguishable lines or an ambiguous split, preserve the multiset and hold rather than manufacture a globally stable line identity. A known external event ID can be deduplicated within `(source connection, event type, event ID)`; same key with conflicting payload is a conflict, not an overwrite. Identical observations in different batches remain distinct evidence. `A → B → A` must not be collapsed into a single A.

**Commitment** is a scoped, explainable quantity owed against a pool, with a channel identity, event/observation references and frozen mapping versions. The following is a proposed derived lifecycle, not a mapping from raw Ozon statuses:

1. `unresolved`: identity, coverage, source ordering, overlap, cancellation or line meaning is not proven; capacity is unknown.
2. `open_unreflected`: an obligation is supported and proven outside the selected source reserve/physical baseline. It contributes once to `U`.
3. `open_reflected`: evidence ties the same quantity to the selected source reserve or a proven source physical reduction; it does not also contribute to `U`. Store which baseline and which portion; never infer reflection from amount equality.
4. `release_pending`: cancellation or fulfillment is observed, but release/physical effects or source ordering remain unproven; do not increase capacity on this evidence alone.
5. `closed`: authoritative evidence and policy prove the obligation no longer consumes the pool or its consumption is represented in a later source baseline. A reversal/correction creates new evidence and may return the projection to unresolved.

Partial reflection or cancellation is represented by explicitly quantified portions with independently proven coverage, not by changing a whole-order boolean. Transitions append reasoned evidence and update a rebuildable projection atomically. Conflicting or incomparable observations are unresolved. No source update timestamp means local observation order is deterministic storage order only. Neither arrival time nor an assumed status rank establishes external chronology. Mapping versions are frozen at *interpretation/decision* time; current mappings are not retroactively historical facts.

**Calculation** is an immutable decision: exact input and mapping IDs, policy/version, observation times, trusted coverage/watermarks or bounds, quantities, reasons and expiry. Result is `READY_CONDITIONAL` with an explicit as-of/bound and integer quantity only when every gate holds; `UNKNOWN` for missing or conflicting evidence; `BLOCKED` for known unsupported configuration/policy. Both latter results have **NULL quantity**, never an implicit zero. A real zero is allowed only when the gates hold and the calculation yields zero. A local no-write decision does not remove stock already offered on Ozon: surface an urgent exposure warning and require an operator-controlled, independently authorized mitigation. This design does not perform that mitigation.

## Conditional calculation model

For a single pool and baseline, assume all values use the same verified unit and scope:

* `P`: source physical stock at the baseline; `R`: all source-side reserved units applicable to that pool, including conservatively assigned unallocated reservations.
* `U`: the disjoint sum of obligations proven not represented in `P`'s physical reduction or `R`, including Ozon and other channels, and any pre-posting reserve not already represented by those obligations. `U` is **not** `sum(all postings)` and is not automatically Ozon `reserved` plus posting lines.
* `S`: configured nonnegative business safety stock. `D`: independently justified upper bound for other potentially unseen reductions between the baseline and evaluation/decision validity. Its risk window and event sets must not overlap `U` or `R`; coverage and evidence for the bound are required. A guessed buffer or a freshness TTL alone is not proof.
* `C = max(0, P - R - U - S - D)` in exact decimal arithmetic, **only when** baseline consistency, full scope/visibility, reflection attribution, units, status/line semantics, mapping versions, unassigned reservations and all negative-change bounds are evidenced. Incoming is excluded. Unsupported negative source values, undefined unit conversions or rounding policies are `UNKNOWN`/`BLOCKED`, not silently clamped source inputs. The final nonnegative clamp is allowed only after validation. Integer conversion requires a verified policy that never rounds upward; absent such a policy, block.

`C` is a conservative *conditional free capacity*, not proof of what Ozon currently exposes or that an eventual write is safe. If any prerequisite is unknown, no arithmetic output is publishable. Read-only V1 may show raw inputs and a reason, but must not show a speculative value as ready. TTL, local time and completed pagination do not alone prove the conditions; current STYK inputs do not supply the required cross-system attribution, unassigned-reserve coverage or consistent cut. Any experimental numerical example must be labeled hypothetical.

For future multiple channels, let `E_i` be the **upper bound** of still-sellable exposure on target `i`, including accepted, in-flight and unknown-outcome writes. After each commitment is represented once in `R` or `U`, an atomic allocator must keep `Σ E_i ≤ C` using all targets and hold an allocation until external exposure is proven removed. A separate quota per target may be used only if the total respects this bound; don't subtract the same already-reflected reservation a second time as an exposure. Ozon's reserved quantity may overlap posting obligations and must be reconciled, not summed by name. In V1 shared pools are blocked rather than allocated. A mathematically valid baseline can still be invalidated immediately by uncontrolled source or marketplace actions; safe automation needs exclusive control or a defensible bound through the write and until the next correction, plus operational acceptance of residual risk.

### Worked examples (hypothetical, fully evidenced units)

Each row assumes an authoritative compatible baseline, exhaustive obligation coverage, unassigned reserves handled, `D=0`, and verified single-unit conversion. Except in the two-channel example, assume no other target exposure. These assumptions are **not provided by today's imports**. The listed `C` is a conditional free capacity, not a live Ozon instruction.

| Case | `P` | `R` | `U` | `S` | Result and reasoning |
| --- | ---: | ---: | ---: | ---: | --- |

## Proposed PostgreSQL model and transaction boundaries

This is a schema proposal, **not a migration**. Use exact `numeric` for source units; require nonnegative commitment portions and integer channel units after verified conversion. Use restrictive foreign keys (`ON DELETE RESTRICT`), an application role without evidence UPDATE/DELETE, and append-only correction records. A privileged administrator can override SQL privileges; audit/backup and operational controls remain necessary. Never store secrets or customer PII in these tables.

| Proposed relation | Key data, constraints and indexes |
| --- | --- |
| `tenant_connection` | `(tenant_id, connection_id)` PK; source, verified external account ID, state and ownership provenance. Default unique `(source, external_account_id)` across tenants so the same physical account cannot be double allocated under different tenant labels. A future explicitly shared owner/pool model is needed before relaxing this. Composite uniques support scoped FKs; credentials are out of scope. |
| `pool` | Tenant, MoySklad connection, warehouse ID, kind (`product`/`variant`), item ID, unit; unique `(connection_id, warehouse_id, kind, item_id)` and scoped `(tenant_id,id)`. Composite FK to owned source connection. One row is the coordination lock for that physical pool. |
| `warehouse_binding` | Tenant, both owned connections and warehouse IDs plus frozen warehouse mapping-history `(mapping_id,version)`. Partial unique indexes on active `(MoySklad connection, warehouse)` and active `(Ozon connection, warehouse)` enforce one-to-one across account pairs. Scoped composite FKs and checks require the historical mapping and both connection owners to agree. Retain inactive versions. |
| `pool_target_binding` | Tenant/pool, scoped warehouse binding, Ozon connection, warehouse, product ID, offer ID and frozen product mapping-history `(mapping_id,version)` reference. Partial unique indexes for one active target per pool and one active binding per `(tenant, Ozon connection, warehouse, product)` and per `(tenant, Ozon connection, warehouse, offer)` in V1; check identifiers, warehouse binding, units and account-pair agreement. SKU is evidence, not an interchangeable key. History is retained on replacement. |
| `source_evidence` and `posting_evidence_link` | Typed references to existing exact stock rows `(import_id,kind,external_id,warehouse_id)` and posting observation/line, respectively; tenant/connection, source/account, original times, time basis, coverage, baseline and status. Add composite unique keys/FKs to legacy parent tables where required and enforce the verified ownership join: `source_imports` alone has no tenant. Reuse observation payload; never copy a NULL quantity as zero. | `commitment_identity` | Tenant, channel connection, posting identity and a genuine documented line/event identity **if available**, plus pool and frozen mapping versions. Scoped unique key for genuine identities. Without stable line identity, preserve observation-local line sets and block ambiguous interpretation rather than impose an ordinal-based global unique key. |
| `commitment_evidence` | Append-only scoped commitment/pool reference, source observation/event, type, exact quantity and optional source event/version, provenance, received time, source time/basis. Partial unique `(connection_id,event_type,source_event_id)` only where a source event ID is actually supplied; same ID/different payload fails. Distinguish an observation reference from an event ID. Index `(tenant_id,commitment_id,id)` and `(tenant_id,pool_id,id)`. |
| `reflection_evidence` | Immutable positive portions linking a commitment to a specific source baseline and attributable source reservation or physical movement, plus coverage and provenance. Composite FKs include tenant, pool and relevant connection. In a transaction lock the commitment and baseline allocation; enforce `sum(reflected portions) ≤ proven commitment` and `sum(attributed to source part) ≤ proven source part`, plus non-overlapping ranges/identities where supported. Aggregate cross-row bounds require locked updates/constraint triggers, not a simple CHECK. Unknown attribution blocks rather than assuming 0. |
| `commitment_projection` | Rebuildable scoped `(tenant,commitment_id)` current state, outstanding/reflected/unreflected portions, basis and revision. `CHECK` portion nonnegativity and per-row totals; enforce transition/coverage in a pool-locked transaction. Unknown ordering is explicit. Delete/rebuild this projection without deleting evidence. |
| `calculation_decision` | Immutable pool, target binding versions, policy version, input references/baseline, source/observation times, expiry, `READY_CONDITIONAL`/`UNKNOWN`/`BLOCKED`, exact `P,R,U,S,D`, output and reason codes. CHECK output is non-NULL and nonnegative only for `READY_CONDITIONAL`; all others NULL. Index `(tenant,pool,id DESC)`. Decision creation uses a consistent DB read, then validates revisions under a pool lock; no network inside the transaction. |

Future, **not V1**, separate `publication_intention` (immutable target, decision/version, target sequence, idempotency key if supported, intended quantity and expiry), `publication_attempt_event` (append-only started/ack/rejected/unknown plus per-item result), `target_lane_projection` (one unresolved operation per target, lock/revision), and `reconciliation_evidence` (read time, observed target values, status and provenance). Unique `(tenant,target,sequence)` and an operation key scoped to the target protect local duplication. Composite FKs must bind every intention/attempt/evidence to the same tenant, connections and target. A partial unique active lane and `SELECT ... FOR UPDATE` serialize local intentions; they cannot fence a request already accepted by Ozon. The outbox must have explicit operation types and unknown outcomes, not reuse mock failure semantics. An intent and its outbox entry commit together; HTTP occurs after commit, outside transactions. No schema addition by itself grants cross-tenant authorization or exactly-once effects.

Existing mapping history currently models only version 1 and has no replacement/revocation workflow; introduce immutable new versions and compatible scoped constraints before relying on historical references. Backfill legacy evidence only when ownership and time basis are demonstrable; quarantine ambiguous rows rather than assign them to a tenant or fabricate timestamps. Existing source and posting observations remain intact.

## Recovery, reconciliation and external state

Maintain four separate facts: **desired** (a particular valid calculation), **last attempted** (request sent or possibly sent), **last acknowledged** (per-item API acceptance), and **last verified** (an independently observed external state with time and semantics). An acknowledgment is not a verification; a newer read may still be stale or refer to different stock semantics. Each fact retains its own time, scope, version and uncertainty.

For a future writer, the proposed per-target operation transitions are `planned → dispatching → acknowledged | rejected_proven | unknown`. Persist `dispatching` before attempting the call; a crash after that point is unknown unless separate evidence proves no send. Only a proven pre-send failure can return safely to a bounded queue. `acknowledged → verified` requires a suitable independent read and proven ordering, and can later become `drift_detected` as external state changes. `unknown → resolving → verified | rejected_proven` requires sufficient evidence; otherwise it remains blocked for operator review. Superseding a plan cannot erase an already-dispatched attempt. These are operation states, not posting or commitment states.

* Incomplete read, missing row, stale source, changed mapping, unsupported status, unknown coverage or unresolved source order: invalidate the decision, retain old evidence, mark `UNKNOWN`/`BLOCKED`, and require new evidence. Do not replace a known observation with a fictitious zero. Alert on previously offered exposure.
* Crash before a request is provably sent: only a **durably recorded and verifiable** pre-send boundary permits safe requeue. A crash after the send could have happened, response loss, ambiguous 5xx, or lease expiry becomes `unknown`, never confirmed failed. An expired worker can still complete externally. Do not hold a DB transaction over the call.
* On unknown outcome: pause the target lane, prevent automatic replay and newer conflicting intentions, preserve maximum possible external exposure, and gather supported readback plus per-item response/operation evidence. Retry only with verified external idempotency/conditional-write semantics or a documented safe reconciliation and quiescence protocol. A single matching readback cannot prove an older request will not take effect later; if bounded in-flight completion or external sequencing cannot be established, require manual resolution and keep blocked.
* When readback differs, preserve the observation and classify convergence, mismatch, stale read, reserved-stock interpretation or unknown; do not assume failure or immediately overwrite. Recompute from fresh evidence and mappings. Partial batch acceptance is tracked per target. Manual resolution must record actor, evidence and reason; no unaudited transition to success.

Operationally, monitor decision age and coverage gaps, unexplained/unassigned reservations, unknown operation age, lane backlog and still-sellable exposure. Escalate with an accountable owner and a documented manual procedure. A healthy worker or an empty outbox is not a safety signal when evidence or an external outcome is unknown.

## Scope, phases and go-no-go

1. **Read-only V1:** ownership registry and scoped evidence references; single pool/target validation; deterministic `UNKNOWN`/`BLOCKED` explanations and immutable decision records; validate statuses, overlap and source freshness without inventing missing data. No network side effects. The first slice should honestly return unknown for today's insufficient inputs.
2. Establish source-account/permission and unit contracts; obtain an authoritative posting/reservation crosswalk, unassigned reserve coverage, source baseline/coverage semantics, Ozon pre-posting reserve coverage and experimentally validated bounded delay. Add audited mapping lifecycle and a justified negative-change bound. Contract-test sanitized test accounts with separate authorization; do not treat tests as a universal guarantee.
3. Add read-only reconciliation, replayable ledger projections, per-pool concurrency and failure simulations. Only later design a separate writer with transactional intentions, per-target lanes, unknown outcomes, safe retries, stale-decision checks and operational recovery.

**No-go for real Ozon stock writes** until all of the following are demonstrated and reviewed: current official Ozon write/read semantics and item-level partial results; confirmed Ozon reserved/pre-posting coverage and its overlap with source reservations; authoritative source reservation attribution and unassigned reserve handling; consistent or conservatively bounded source/posting coverage including page drift and uncontrolled decrements; verified units and non-upward conversion; exclusively owned pool and every competing exposure accounted for; authenticated tenant/account ownership; durable mapping versions and concurrency constraints; evidence-backed maximum staleness/expiry and on-call mitigation; tested outbox unknown-outcome recovery, reconciliation and prevention of stale external writes; end-to-end test-account validation and explicit operator authorization. A conditional calculation, successful unit tests, HTTP 200, or the existing mock worker is not sufficient. If an external API cannot provide ordering/idempotency or safe quiescence, automatic writes remain no-go.
