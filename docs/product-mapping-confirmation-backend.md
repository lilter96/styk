# Product mapping review and confirmation backend

The local authenticated operator API can create and inspect an immutable review of one Ozon product and one exact MoySklad product or variant. `POST /api/product-mapping-reviews` accepts JSON fields `tenant`, `ozon_account`, `moysklad_account`, `product_id`, `target_kind`, `target_id` and `evidence_class`. It requires the configured loopback Origin and an active operator session. The server resolves both latest eligible completed imports and rejects missing registrations, missing identities, unsupported evidence and invalid requests. It returns a random review ID, import references, existing mapping version if present, conflict flag and status. Import IDs, session audit identifiers and principal types are never accepted from the request.

`DETERMINISTIC_CANDIDATE` means the existing matching engine found the exact selected item by imported identifiers. `OPERATOR_ATTESTED` permits an explicit selection with differing identifiers; its confirmation records an operator's business assertion. Neither establishes independently verified identity. `INDEPENDENTLY_VERIFIED` is rejected because no verification provider exists. A review alone is not an approval and creates no mapping, mapping history or publication task.

`GET /api/product-mapping-reviews/{id}` requires the same active local operator session that created the review. The server revalidates registered scopes, selected identities, eligible import IDs and mapping state. It returns `CURRENT`, `EXPIRED`, `STALE_SOURCE` or `STALE_MAPPING`. A newer completed import makes a review stale even when selected values match; identical deduplicated imports keep their original ID. The server captures each import’s stored fingerprint and hashes selected source fields and mapping state to detect differences present at inspection. Migration 18 does not backfill immutable pre-existing reviews: reviews without both captured import fingerprints are `STALE_SOURCE` and require a new review. A privileged database actor can alter existing source data outside the application's locking protocol; hashes cannot reveal a change that was later reverted and do not make old source rows immutable snapshots.

`STYK_REVIEW_LIFETIME` defaults to 5 minutes and must be positive and at most 10 minutes. Stored reviews and their original revision references are immutable; stale reviews are never refreshed. Review and source/account references use restrictive foreign keys. Migration 18 refuses rollback if newly captured review fingerprints or confirmation records exist; the review migration also refuses rollback while reviews exist.

## Confirmation

`POST /api/product-mapping-reviews/{id}/confirm` accepts only an authenticated local operator session, the exact configured loopback Origin and `application/json` (optionally with charset). The review must belong to that same session. A request body is limited to 4 KiB and has this shape:

```json
{"idempotency_key":"client-generated-key-1","acknowledge":true,"explanation":"Operator checked the product identity"}
```

`idempotency_key` is required, client-generated, and 1–128 ASCII letters, digits or `._:-`; `acknowledge` must be explicitly true for a new confirmation. `explanation` is optional and at most 1,000 UTF-8 bytes. Do not put credentials or customer data in it. Client-supplied tenant, account, import revisions, evidence class, principal and session audit ID are rejected. The review is authoritative. A successful response returns `mapping_id`, `mapping_version`, `review_id`, `evidence_class`, `confirmed_at` and `idempotent_replay`.

The server loads the session-scoped immutable review, acquires the existing transaction-scoped advisory locks in order `ozon:<account>`, `moysklad:<account>`, `matching:<tenant>`, and checks a previous successful outcome before checking review expiration. For a new outcome it revalidates registered account scope, both completed imports, exact identities, source and mapping fingerprints, expiration and existing mapping conflicts while holding the locks and source-row read locks. The deterministic class is rechecked against the existing matching engine; an attested selection does not require matching article or code. Selected observation rows, existing mapping rows and source-import metadata are protected by row locks while validating and writing. A deferred database guard checks expiration again at commit. No external HTTP request occurs in this transaction.

A new confirmation atomically inserts the mapping, its review-bound history, an immutable audit and an immutable idempotency outcome. The audit records source and target identities, both import references, evidence class,Merchant sessions use persistent identity, workspace membership and role checks. Historical `LOCAL_OPERATOR_SESSION` audit records are preserved as historical evidence; they do not enable login. Session identifiers and idempotency keys are not returned in mapping history. A lost session cannot undo a committed transaction; inspect scoped mapping history after signing in again.

Idempotency is scoped by review, creating session and key. A versioned canonical fingerprint binds review ID, acknowledgement and the exact explanation. The same key and semantic request return the recorded result with `idempotent_replay=true`; changing the payload returns `IDEMPOTENCY_CONFLICT`. JSON whitespace or key order do not affect this fingerprint. A successful result remains replayable after the review expires or source imports change, as long as the same session remains active. A new key cannot start a confirmation after expiration. A timeout or lost response may leave the outcome unknown to the caller: retry the same key, rather than assuming failure. This guarantee concerns the local PostgreSQL transaction only; it makes no exactly-once claim for external effects.

Failures are reported with stable codes: `UNAUTHORIZED`, `FORBIDDEN`, `INVALID_REQUEST`, `REVIEW_NOT_FOUND`, `REVIEW_EXPIRED`, `REVIEW_STALE`, `MAPPING_CONFLICT`, `IDEMPOTENCY_CONFLICT` and `PERSISTENCE_FAILURE`. Raw database errors are not returned. `PERSISTENCE_FAILURE` can include an uncertain commit outcome; use the same key and session to reconcile it.

Migration 18 adds ordinary unique constraints and foreign keys to existing review and history tables; these can scan data and acquire locks. Plan and review it before any production migration. Its down migration refuses to discard captured review fingerprints or confirmation evidence. No production database was migrated during this work.

## Session and legacy limitations

 `LOCAL_OPERATOR_SESSION` is a shared local principal, not a verified individual. Logout cancels in-flight requests where possible, but cannot undo a transaction already committed. Sessions are in memory, so expiration, logout or restart prevents a new session from replaying or inspecting an old review. After a session is lost, a newly authenticated local operator can inspect the committed mapping through `GET /api/product-mapping-history` with the registered tenant, account pair and product. Review-bound history includes its evidence class, review ID, principal type and explanation; session identifiers and idempotency keys are not returned. The operator may also inspect audit tables directly as a trusted local database administrator.

The existing `matching confirm` CLI remains a trusted administrative path. It rechecks current deterministic candidates and writes its legacy mapping and history atomically, but it does not validate a durable review, reviewed revisions or tenant registration, and does not claim the new API's session or idempotency guarantees. It is not an independent verification source. Production use still requires individual authentication, tenant authorization, secure session handling, audit review and deployment controls; local database access is not row-level security.

A confirmed mapping, including `OPERATOR_ATTESTED`, does not establish unit or pack equivalence, warehouse ownership, reservation attribution, source baseline consistency, competing exposure or a safe publication quantity. The stock decision database still accepts only UNKNOWN or BLOCKED and confirmation creates no stock decision or publication task. The React console supports explicit review and confirmation; no external marketplace writes are implemented. See [browser workflow](product-mapping-review-v1.md).
