# Ozon bounded import: work in progress

Both administrative imports now use bounded traversal. The catalog importer traverses both product visibility groups, all warehouses and associated stock before persistence. A partial traversal is never passed to persistence as a completed batch. These changes have been verified with mocks and PostgreSQL; live persistence has not been validated.

The catalog CLI accepts `-max-requests`, `-max-attempts`, `-max-pages`, `-max-products`, `-max-warehouses`, `-max-stock`, `-max-response-bytes` and `-max-duration`. The posting CLI accepts the same request, attempt, page, response and duration flags plus `-max-postings`. Defaults are 100 logical requests, 100 network attempts, 100 listing pages, 4 MiB per response and three minutes overall; catalog defaults additionally permit 1,000 products, 1,000 warehouses and 10,000 stock observations, while postings default to 1,000. Logical requests include detail calls; pages count listing calls; attempts count actual HTTP sends including retries. Bodies are read through a byte limit. Counters and a typed `LIMIT_REACHED` resource accompany failures; no partial result is returned.

Each CLI outputs a structured execution result with `COMPLETE_TRAVERSAL`, `LIMIT_REACHED`, `CANCELLED`, `API_FAILURE`, `INVALID_RESPONSE` or `PERSISTENCE_FAILURE`, counters and elapsed duration. A database timeout or failure during persistence is a persistence failure. Non-completion exits unsuccessfully. The overall deadline starts before database access and applies through traversal, validation and persistence. The store separately applies `QUERY_TIMEOUT`; the earlier deadline wins. Network traversal occurs before the database transaction. The existing PostgreSQL transaction atomically inserts each completed batch; a commit connection failure can leave the commit outcome uncertain and should be inspected before retrying. Completed traversal does not establish exhaustive visibility or a point-in-time snapshot.

Seven bounded live read requests were made against the owner-authorized account: four warehouse page requests, two product-list requests and one FBS posting-list request. The repeated warehouse check used independent response objects: the first two page IDs differed, the cursor progressed, both rows included the rFBS classification field, and the second page indicated further pages. Full traversal, all identities and completion remain unverified. One-day historical posting window, seven to eight days before the request, returned an empty top-level posting list; this does not prove there are no other postings. Product-list preflight reported 9 non-archived and 24 archived items; only the first item of each group was read. This is a local observation, not proof of source completeness or stable counts. No live stock query or full import was performed during this work; the earlier one-off stock probe had no rows, which is not zero stock.

No PostgreSQL live persistence or Integration Doctor run was performed. No mappings, outbox tasks, external writes or stock publication were created. The focused bounded catalog and posting tests use synthetic HTTP responses and PostgreSQL to verify completion, budget exhaustion, cancellation, database timeout, transaction rollback and preservation of an earlier batch. Broader real-account contract validation, live stock values and posting details remain future work.
