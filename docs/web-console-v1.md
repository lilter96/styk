# Web console V1

The console is a local operator tool with explicit product mapping confirmation in the local database. The React/TypeScript Vite application uses React Router and TanStack Query; the Go API queries PostgreSQL and calls the existing matching and Integration Doctor logic. No browser code calls a marketplace, and no screen commits inventory or schedules publication. Account registration is a trusted local administrative assertion, not authenticated tenant authorization.

## Local setup

1. Start the development PostgreSQL instance with `make up`, set `DATABASE_URL` to the local database, and run `make migrate`. Existing registrations and imports are required for real observations; use the normal trusted administrative and import commands documented in the README. Do not use production data for tests.
2. In the API terminal set `HTTP_ADDR=127.0.0.1:8080`, `STYK_CONSOLE_ORIGIN=http://127.0.0.1:5173`, and set `STYK_OPERATOR_SECRET` to a locally generated random secret of at least 32 characters. Keep it out of shell history and version control. For example, use a silent shell prompt (`read -rs STYK_OPERATOR_SECRET; export STYK_OPERATOR_SECRET` in Bash or Zsh), then run `go run ./cmd/api`. The operator secret is separate from marketplace credentials; none are required for the console.
3. In another terminal run `cd web && npm ci && npm run dev`, then open `http://127.0.0.1:5173`. Sign in with the operator secret, enter a tenant ID, and select registered accounts. The secret is sent to the local API only and is not included in the JavaScript bundle or browser storage.

If the operator secret is absent, business endpoints are not installed. The API defaults to loopback. `STYK_ALLOW_REMOTE_BIND=true` explicitly permits a non-loopback listener for health endpoints only; the operator console refuses to start on a non-loopback address even with that opt-in. Use the same loopback origin in the browser and `STYK_CONSOLE_ORIGIN`, including port. The Vite dev server proxies `/api` to the local Go API. The frontend production build is an artifact, not a deployment or a Go-served application.

## Security boundary

Authentication uses a random, in-memory eight-hour session represented by an HttpOnly, SameSite=Strict cookie. Sessions disappear on API restart. Login and logout require the exact configured loopback Origin; data requests reject foreign origins, non-loopback Host values and non-loopback peers. Responses have `Cache-Control: no-store`. The API never returns credentials or raw responses. Local HTTP has no TLS, and the shared operator secret grants access to any registered local tenant: this is not commercial authentication, an authorization system, or a defense against other users or processes with access to the same machine. Do not expose it through a remote proxy or shared host. Production use requires real identity, tenant authorization, TLS, session/CSRF controls, audit and deployment review.

## API and screens

The authenticated GET endpoints are `/api/registrations`, `/api/diagnostics`, `/api/products`, `/api/warehouses`, and `/api/stock`; `/api/session` handles local login, session checking and logout. Each data query requires a tenant and, where appropriate, registered source accounts. Failed requests return a machine-readable error code. Queries use the configured database timeout and request cancellation. Product, warehouse and stock pages are bounded to 50 rows; account lists are capped at 100. Matching loads at most 2,000 target items and 2,000 mappings per page, displays at most 20 candidates per item, and reports truncation instead of asserting uniqueness when the universe is too large. The product page requires both accounts. Filters cover search, archived status and confirmed/unconfirmed mapping status.

Overview distinguishes registered sources, completed imports, observation age and unchecked live connectivity. Products show the existing deterministic engine's suggestions; a suggestion is not confirmation. Warehouses show confirmed mappings only for the selected account pair and retain source-specific stock fields. No row means no observation; null means unknown; reported zero remains zero. Observations older than one hour are flagged stale; age is not proof of source freshness. Diagnostics shows Integration Doctor's actual checks and decision status. A missing pool is NOT_CHECKED; UNKNOWN and BLOCKED do not imply zero. READY_CONDITIONAL is never synthesized by the console.

The current account selectors require manually entering an existing tenant. The UI can explicitly confirm product and warehouse mappings through revision-bound reviews, but does not register accounts, trigger imports, manage users or provide stock publication. An operator-attested mapping is not independently verified identity. See [product mapping review](product-mapping-review-v1.md) and [warehouse mapping review](warehouse-mapping-review-v1.md) for audit and recovery limitations.

## Verification and limitations

Run `npm run lint`, `npm run typecheck`, `npm test` and `npm run build` in `web`. The Playwright smoke test (`npm run test:browser`) requires the Go API and Vite running on the default loopback ports and a **disposable** database seeded with `go run ./cmd/doctor -demo -format json`. It uses the synthetic tenant `doctor-synthetic`, synthetic accounts and the synthetic operator secret specified in `web/e2e/smoke.spec.ts`; never use that secret for a real workspace. Install the browser with `npx playwright install chromium`. The demo inserts synthetic evidence and must not be run against a production database.

The console displays existing database evidence only. It does not establish that APIs are currently reachable, permissions are complete, imports represent atomic snapshots, missing stock is zero, reservations are attributed, or competing exposures are controlled. Browser automation and synthetic demo results are not live integration verification.

A local smoke run against the one-product synthetic fixture measured approximately 1 ms for the product endpoint and 17 ms for diagnostics. These single-run loopback measurements are only a development sanity check, not a capacity or production latency claim.
